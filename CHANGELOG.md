## [1.3.4] - 2026-11-12

A patch release for one defect in every release so far, found on AWS: an EKS install could lose every Service in the cluster to the AWS Load Balancer Controller's webhook certificate, which its chart makes anew on every render. On AWS it first ran by hand on 12 November 2026 ([run 43268704872](https://github.com/heyvaldemar/aws-eks-reference-platform/actions/runs/43268704872)) and passed. *(Updated on 2026-11-12.)*

### Fixed

- An EKS install could lose every Service. A run started by hand on 1.3.3 ([run 43119033426](https://github.com/heyvaldemar/aws-eks-reference-platform/actions/runs/43119033426), on `3f2dff1`, 11 November 2026 at 23:20 UTC) ran prometheus-operator v0.95.2 on both arm64 nodes, the fix of 1.3.3, and failed on another defect. The AWS Load Balancer Controller chart 3.6.2 makes its webhook CA, certificate and key with `genCA` on every render (helm's `lookup` sees no cluster under Argo CD, so `keepTLSSecret` cannot reuse them). A later sync applied a second render's Secret and `caBundle` while the controller's pods, started on the first Secret, kept serving the first certificate for the rest of the run. Which sync it was is not in the run's evidence: the one operation it keeps, three minutes after the first sync, applied a single CRD, and its Argo CD logs begin after that. *(Corrected on 2026-11-12: this said the sync three minutes after the first applied them.)* Its Service webhook, `failurePolicy: Fail`, then rejected every Service create and update with `x509: certificate signed by unknown authority (possibly because of "crypto/rsa: verification error" while trying to verify candidate authority certificate "aws-load-balancer-controller-ca")`, so the cert-manager, external-secrets and Kyverno webhooks had no Service, the secrets `grafana-admin` and `demo-message` were never made, and 13 of 19 Applications stayed OutOfSync. The destroy job, which also looks for residue, passed; the run cost about $0.33. Every release so far is affected: the chart has made its certificate this way since 1.0.0, and no release held it. The EKS runs that passed (15 October by hand; 21 October, 28 October and 4 November on schedule) passed on the order things happened to start in: the scheduled run of 11 November on `71440e7` shows the controller synced again 2 minutes 17 seconds after its first sync, and the webhook kept working. On a cluster that hits it, the run's `diagnose.txt` shows the x509 line above for each Application that holds a Service. The aws-load-balancer-controller Application now ignores the Secret `aws-load-balancer-tls`'s `/data` and both webhook configurations' `caBundle`, with `RespectIgnoreDifferences=true`, so a sync keeps the pair the first sync made. kind runs no load balancer controller. On AWS the fix first ran by hand on 12 November 2026 ([run 43268704872](https://github.com/heyvaldemar/aws-eks-reference-platform/actions/runs/43268704872), on `10cc525`, this release plus a Dependabot setting): 14 of 14 checks passed and all 19 Applications were Synced and Healthy; the controller synced again three minutes after its first sync, as in the run that failed, and no webhook call failed with an x509 error. The run cost about $0.21 and left nothing behind. *(Updated on 2026-11-12.)* On a cluster already in this state, restart the controller once (`kubectl -n kube-system rollout restart deployment aws-load-balancer-controller`) so its pods load the certificate the webhooks now name.
- One webhook could stop every Service in the cluster. The controller's Service webhook, `failurePolicy: Fail` with no opt-in selector, only set `loadBalancerClass` on LoadBalancer Services that had none. It is off (`enableServiceMutatorWebhook: false`), and the Gateway's Service, the platform's one LoadBalancer Service, names `loadBalancerClass: service.k8s.aws/nlb` itself, the value the webhook set on clusters made before, which the API server would not let change.

### Added

- A static check, `render-drift` (`scripts/check-render-drift.py`): each environment is rendered a second time, and every field whose value differs between the two renders must be covered by its Application's `ignoreDifferences`, with `RespectIgnoreDifferences=true` among its syncOptions. It prints paths, never values. On `3f2dff1` it reports 12 fields, all the controller's and on EKS only (the Secret's three keys and nine `caBundle`s); with the fix there are 11, the Service webhook's `caBundle` gone with it, and all 11 are held. Two plants: the sync option removed, and a rule naming a Secret the chart does not make.
- A static check, `webhooks` (`scripts/check-webhooks.py`): a rendered Mutating- or ValidatingWebhookConfiguration that fails closed may match core pods, services, secrets, configmaps, namespaces or service accounts, apps workloads, or a wildcard only for objects that opt in, by `matchLabels` or an `In` or `Exists` expression in its namespace or object selector. Of 27 webhooks rendered on `3f2dff1` it reports one, the Service webhook above. One plant: that webhook turned back on. Static checks: 13, plants: 33.

## [1.3.3] - 2026-11-11

A patch release for one defect in 1.3.1 and 1.3.2: on EKS they do not come up, because the prometheus-operator image they pin has no arm64 and the system nodes are Graviton. On AWS it first ran by hand on 11 November 2026 ([run 43119033426](https://github.com/heyvaldemar/aws-eks-reference-platform/actions/runs/43119033426)): the operator came up on the arm64 nodes, and the run failed on another defect, fixed in 1.3.4. *(Updated on 2026-11-12.)*

### Fixed

- 1.3.1 and 1.3.2 do not come up on EKS. The weekly run on the AWS account failed on 11 November 2026 ([run 42981638335](https://github.com/heyvaldemar/aws-eks-reference-platform/actions/runs/42981638335), on `71440e7`, its first on 1.3.1's pins): prometheus-operator stayed in ImagePullBackOff with "no match for platform in manifest", and kube-prometheus-stack stayed OutOfSync and Degraded while the other 18 Applications were Synced and Healthy; the run's destroy job, which also looks for residue, then passed. 1.3.1's move to kube-prometheus-stack 93.1.0 (`8a5004a`) pinned prometheus-operator and its config reloader v0.95.1, whose image indexes list five manifests each, every one for linux/amd64 (upstream's own report: [prometheus-operator/prometheus-operator#8953](https://github.com/prometheus-operator/prometheus-operator/issues/8953)), and the system nodes are Graviton (arm64). Every check before AWS passed, because every runner is amd64. Now kube-prometheus-stack 93.2.0, with prometheus-operator and the config reloader v0.95.2, whose indexes list linux/amd64, linux/arm64 and three more. The chart also moves its defaults to Alertmanager v0.35.0 and Grafana 13.3.1, pinned by digest with them. Alertmanager v0.35.0 removes `--enable-feature=auto-gomemlimit` and renames eventrecorder outputs; the operator passes `--enable-feature` only from `spec.enableFeatures`, and the platform sets neither. Alertmanager runs on EKS only, so the next scheduled EKS run is the first to run v0.35.0.

### Added

- A static check, `platforms` (`scripts/check-platforms.py`): every pinned digest's manifest, read anonymously from its registry, must list each platform its nodes run, linux/amd64 on kind and, on EKS, the architecture of the system nodes' `ami_type` and every one the Karpenter NodePools allow (today linux/amd64 and linux/arm64). A registry that throttles or fails is asked three times, and a digest it does not answer is reported and fails the check. Two plants: the v0.95.1 operator pin of the 11 November run, and a NodePool that allows s390x. `check-platforms.py selftest` runs its logic against a fixture registry. Static checks: 11, plants: 30.

## [1.3.2] - 2026-11-09

A patch release for one defect in 1.3.1: Argo CD 3.6 counted a Kyverno ValidatingPolicy Degraded when Kyverno 1.19 wrongly reported it not ready, and an install could time out on it. Nothing else changes.

### Fixed

- An install of v1.3.1 could stop on a policy that worked. Kyverno 1.19 can leave a ValidatingPolicy at `ready=false` with "WebhookConfigured: Policy is not configured in the webhook." while the ValidatingAdmissionPolicy generated from it stays in place (the upstream report finds admission unaffected; these runs did not test admission while a policy was stuck; clarified on 2026-11-09), at random among policies applied together ([kyverno/kyverno#17088](https://github.com/kyverno/kyverno/issues/17088), fixed by commit [d633c49](https://github.com/kyverno/kyverno/commit/d633c49a9a65), which is in v1.20.0-rc.3 and not in v1.19.2; the pull request it names no longer opens, so the link goes to the commit, corrected on 2026-11-09). Argo CD 3.6, new in v1.3.1, reads that as Degraded, and the `policies` Application stayed Synced Degraded until the run timed out (kind e2e run 42544332226, installing v1.3.1). On a kind cluster with Kyverno 1.19.2 and our values, five of six batches of our four policies left one or two of them so, unchanged five minutes later, each with its VAP generated and its permissions granted. Argo CD's health check for ValidatingPolicy is now overridden in `argocd-cm` with its own 3.6.1 script changed in one place: on a policy whose VAP was generated, WebhookConfigured=False is not a failure, as Kyverno 1.20 decides it itself. Any other False condition is still Degraded, and admission is still proven by e2e step 4 with Kyverno up and down. Drop the override once Kyverno is on 1.20. A `policies` Application stuck Degraded on v1.3.1 by kyverno#17088 reports Healthy under this override: shown by the offline `argocd-health` check on the recorded status; not observed on a live upgrade (clarified on 2026-11-09).
- `scripts/diagnose.sh` lists every Kyverno policy that is not ready with its failed conditions: Argo CD 3 keeps no per-resource health in an Application, so a Degraded `policies` named no policy.

### Added

- A static check, `argocd-health`: Argo CD's own `argocd admin settings resource-overrides health`, run offline in the Argo CD image `images.yaml` pins with the `argocd-cm` the chart renders, on five recorded policy statuses in `tests/static/argocd-health/`. The status Kyverno 1.19.2 left on `require-image-digest` must be Healthy; a policy missing permissions, or missing from the webhook without a VAP, must be Degraded. Three plants: the override made inert, the override excusing every failed condition, and the override under a key Argo CD ignores without a word. Static checks: 10, plants: 28.

### Fixed

- The freshness check no longer reports a registry that refused it as pins behind. On 27 October about half of its runs met ECR Public's "429 toomanyrequests: Data limit exceeded" for the same three pins (the Docker Official Image redis, the Load Balancer Controller, Karpenter's chart), which resolved from everywhere else, and each run said "3 pin(s) behind upstream" (Verification runs 40586453120, both attempts, and 40598535000 an hour later). A throttled lookup or chart pull is now tried three times over three minutes; if the registry still refuses, the pin is reported as "could not check: ECR Public throttled", the job still fails, and the summary says how many pins could not be checked instead of a count of pins behind. `scripts/check-freshness.py selftest` shows the check a registry that answers 429 every time and fails unless the run fails, says so and stops asking that host; the job runs it first. Verification still holds no AWS credentials.
- The OpenTelemetry Collector ran 0.161.0 while its chart had defaulted to 0.162.0 since chart 0.176.0, and the freshness check never said so: the chart renders the image by digest alone, and the check compares tags. It now runs 0.163.2, chart 0.177.0's default. cert-manager's images are pinned the same way, by digest under the chart's tag, so after this move each image the platform renders was checked by hand: the 29 rendered with a tag against what the tag resolves to today, the six rendered by digest alone against their tag's digest. None differs. `scripts/check-freshness.py` still cannot see an image rendered without its tag. Nor can it see an image a controller compiles in: Envoy Gateway names its proxy's default in its code, not its chart, and v1.9.3 moved it from distroless-v1.39.1 to distroless-v1.39.5 while the pin stayed. Its release notes said so; the proxy is now pinned to the digest v1.9.3 compiles in, which its tag resolves to today.
- Argo CD's application controller ran out of memory upgrading the platform. Moving v1.2.0 to this release's charts, it was OOMKilled again and again at its 1Gi limit and never applied its own update, so the platform never converged (kind e2e runs 40550141772 and 40563291328, nine kills each). Each CRD the upgrade changes, about a hundred here, makes it reload the whole cluster's OpenAPI schema with its cache full; a fresh install, creating them in a nearly empty cluster, fits in 1Gi. Read from its cgroup, the controller that finished the upgrade at 4Gi peaked at 1631 MiB (run 40576202356). The limit is now 4Gi, with `GOMEMLIMIT` at 3600MiB as Argo CD's high-availability guide advises. A value alone would not reach the controller that has to sync it, so `bootstrap/bootstrap.sh`, re-run to move a cluster, gives the running controller both. A first version did that before anything else and did not hold: Argo CD healed the StatefulSet back to the revision its Application still named within twelve seconds (run 40576198900), and the runs meant to test 2Gi had patched in the same order. It now patches once the argo-cd Application names the new revision, before the new chart versions, and checks fifteen seconds later that the limit held (ADR 1, revisited 2026-10-27). The same restarts had made step 5b read no message at all for a refusal earlier that day ("team-b's RoleBinding to admin was not refused: 'no message'", run 40524076167, first attempt); step 5b now starts each escape once the controller is rolled out and Ready, and still needs each refusal within the same two minutes, and a missing refusal names the controller's restarts. `scripts/diagnose.sh` prints how each restarted container's last run ended (the reason, such as OOMKilled, and the exit code), which is what named the kill, and the kubelet's Killing and Evicted events, which outlive a replaced pod. Before its checks, `tests/e2e/run.sh` prints how often the controller's pods started and backed off in the last hour of events: a passing upgrade read 11 starts and 9 back-offs.
- Dependabot updates merge again once both gates are green. The auto-merge ran only when the kind e2e finished, on the belief that it always finishes after Verification; on 2026-10-25 Verification finished later on both Dependabot pull requests (#16, #17), the auto-merge found it still running and did nothing, and both stayed open with every check passing until the fleet heartbeat reported them 45 hours later. It now runs when either gate completes and merges only when both have completed green, one run per commit at a time, and dispatches both on main after the merge.
- The hands-on guide's weekly run prefetches the Docker Official Images from mirror.gcr.io, as the kind e2e does: its scheduled run of 2026-10-18 failed on argocd-redis behind ECR Public's throttling of shared runners.
- Verification's `rendered-manifests` artifact no longer carries private keys. Two charts generate one when they render (the AWS Load Balancer Controller's and External Secrets' webhook certificates; never deployed, since Argo CD renders the charts itself). `scripts/redact-secrets.py` blanks every Secret's values before the upload, after a self-test with a planted key, and the upload is skipped if it fails.
- The README said the EKS run is weekly before any scheduled run had happened, which its own ADR 9 forbids: it now says by hand on 2026-10-15, scheduled weekly from 2026-10-21. The Terraform posture test's plant count was 24 in the README and 27 in its file. The upgrade runbook named four places that hold the Kubernetes version; there are six. The decision index still called ADR 10 design only.

- Every `images.yaml` said `scripts/pin-images.py` moves its pins. No such script ever existed; the header now names `scripts/check-freshness.py`, which reports a pin a chart bump or a re-pushed tag has left behind.
- The kind e2e no longer depends on ECR Public's patience with GitHub's shared runner addresses. Twice on 15 October the upgrade job waited out helm's ten minutes on `argocd-redis` behind "429 Too Many Requests" from public.ecr.aws, while the fresh install on another runner passed all 56 checks. `scripts/kind-prefetch.sh` now pulls every Docker Official Image the platform pins from ECR Public into each kind node from mirror.gcr.io, by the same digest, and names it as the platform does, so the kubelet finds it present and never asks ECR. Both jobs run it, the upgrade job for the previous release's pins as well as this commit's.
- The bootstrap README now says that AWS Budgets e-mails only verified addresses since 30 September 2026: the alerts went nowhere for a day because the verification link from the apply had lapsed. How to send it again is in the same step.
- The daily sweeper failed on the seventh run's state: the lock of a local `terraform destroy` stopped by hand was still in the bucket, and the state still listed a VPC removed by hand. The lock is gone and the state empty. The sweeper itself now cleans in the run's order (`aws-controller-cleanup.sh` before and after a targeted destroy of the cluster), so controller security groups no longer keep a VPC from being deleted.

## [1.2.0] - 2026-10-15

The EKS path, applied to a real AWS account for the first time. Run [38695231460](https://github.com/heyvaldemar/aws-eks-reference-platform/actions/runs/38695231460) on `7040995` applied 101 resources, brought all 19 Applications to Synced and Healthy on EKS 1.37, passed every check in `tests/eks/run.sh`, destroyed everything, found nothing left and estimated its own cost at about $0.20. The seven runs before it failed on things only AWS could show, about $1.09 between them by their own estimates; each is a fix below with a check behind it. The run now repeats every Wednesday.

### Fixed

- The seventh validation run brought 18 of the platform's 19 Applications to Synced and Healthy on EKS, then its teardown left a network load balancer, two controller security groups and two volumes behind, and they kept the VPC from being deleted (cleaned by hand within the hour; the residue search then found nothing). `eks-cleanup.sh` had deleted the root Application, which cascaded through the AWS Load Balancer Controller before the Gateway's Service was gone. It now stops Argo CD first, deletes Gateways (Envoy Gateway would put their Services back), the remaining LoadBalancer Services, Ingresses and Karpenter's NodePools and NodeClaims while their controllers run. `scripts/aws-controller-cleanup.sh` then deletes from AWS's side, by the controllers' tags, what is still there: load balancers and target groups before the cluster goes, instances, security groups and available volumes after it, before the network. The run's teardown and `make eks-down` destroy in that order. `diagnose.sh` now shows certificates, ACME orders and challenges and Gateways.
- What kept Argo CD's root Application `Unknown` on EKS 1.37: the default metrics-server add-on, `v0.9.0-eksbuild.12`, is built with Go 1.27, whose default `jsonv2` experiment makes kube-openapi leak field names into the schema it publishes. The API server then answers `/openapi/v2` as protobuf with 503 while JSON still works, and Argo CD reads it as protobuf ([metrics-server#1868](https://github.com/kubernetes-sigs/metrics-server/issues/1868)). The add-on is held at `v0.9.0-eksbuild.11`, the last build on Go 1.26 (go1.26.6, read from the binary; eksbuild.12 reads go1.27.2), with a test and a planted violation. `bootstrap.sh` now asks for the OpenAPI document the way Argo CD does and fails at once, naming the issue, if the answer is not 200; `diagnose.sh` prints the same answer.
- On a new EKS cluster, Argo CD's controller failed its first cache sync with "error getting openapi resources: the server is currently unable to handle the request": it started while the cluster's aggregated `metrics.k8s.io` API was not answering yet, and left the root Application `Unknown`. `bootstrap/bootstrap.sh` now waits until every APIService is Available before it installs Argo CD and names any that is not, and `diagnose.sh` lists APIServices that are not Available. The fourth run also met a 429 "Data limit exceeded" pulling Karpenter's chart from public.ecr.aws anonymously; the validation run now logs in to ECR Public with its own role first.
- `scripts/aws-residue.sh` failed a teardown that had left nothing: the Resource Groups Tagging API kept listing a deleted NAT gateway, subnet, security group and flow log, and three KMS keys scheduled for deletion. Each tagged ARN is now asked about directly, and only what still exists and is not on its way out counts; a type the script cannot ask about is still reported. The third run cost about $0.31 by the run's own estimate.
- The third validation run reached a running EKS cluster with Argo CD installed and waited 45 minutes on a root Application whose sync stayed `Unknown`, then saved a table that did not say why. `scripts/wait-for-platform.sh` now stops after ten minutes when the root Application has not read the repository, and prints each pending Application's conditions, where Argo CD says why; the run's evidence now carries the Applications as YAML, the repo server's and application controller's logs and `diagnose.sh`.
- The first real apply found two things the mocked-provider tests could not. Karpenter's EventBridge rule for capacity reservation interruptions was named past AWS's 64-character limit once the cluster name carried a run ID (74 characters); the key is shorter now, and a posture test checks every named resource against its AWS limit with the longest cluster name the variable allows, with a planted violation. And the guardrail that keeps workflow roles off the bootstrap's own IAM denied reads as well, so the EKS Terraform could not resolve its own role (`aws_iam_session_context` calls `iam:GetRole`); it now denies every IAM action on them but `Get*` and `List*`, with a test and a planted violation.
- `bootstrap-aws`: the roles trusted the OIDC subject `repo:owner/name:environment:...`, and the first real validation run was refused at the first AWS call. GitHub gives repositories created or renamed after 15 July 2026 an immutable subject, `repo:owner@OWNER_ID/name@REPO_ID:...`, so a name someone gives up and someone else takes cannot match. The new `subject_repository` variable holds that form, defaults to this repository's IDs, accepts the legacy form for older repositories, and must name the same repository as `repository`. Two tests and a planted violation; nothing had been created in the account.

- `bootstrap-aws`: the budget counted credits, as AWS Budgets does by default, so in an account running on promotional credits the $5 and $10 alerts and the $15 kill switch would never fire, and a run left running would spend the credits instead. It now measures usage before credits (`cost_types.include_credit = false`), with a test and a planted violation. The sweeper's daily table leaves credits and refunds out for the same reason.

### Changed

- The EKS validation run is weekly as well as by hand (ADR 9 and ADR 10, revisited): every Wednesday, after Monday's Dependabot updates have merged, and only while the repository variable `AWS_VALIDATION_ENABLED` is `true`, so it stops without a commit. The bootstrap's alerts move to $10 and $20 and its kill-switch to $30, the ceiling for a month of weekly runs.
- ADR 10 and the bootstrap README allow a member account in the maintainer's own AWS Organization, and say why an account that holds other work is the wrong place: the workflow roles can delete what they did not make.
- The README points at [kubernetes-postgres-recovery](https://github.com/heyvaldemar/kubernetes-postgres-recovery), the database a tenant would run here, with the point-in-time recovery that Velero's volume snapshots cannot give it.

### Added

- Live status: every e2e run uploads its checks and measurements (`E2E_RESULTS`), and `.github/workflows/status.yml` rewrites the `status` branch after each run with the last 30 days on main: green days, the streak, the latest checks (`scripts/status.py`). The README's second row of badges reads it.

## [1.1.0] - 2026-10-13

### Added

- `tools/kubectl-tenant`, onboarding as a command. `kubectl tenant new <team>` writes `apps/<team>` from the template and refuses the names the tenant chart refuses, read from `platform/tenant/values.yaml` so the two lists cannot drift apart. `kubectl tenant check <team>` reports from the files alone what admission would refuse: an image without a digest, missing requests, no memory limit, missing probes, a privileged container, the host network. Its tests rebuild `apps/team-b`, made by hand, and fail if the command's result differs.
- `terraform/bootstrap-aws`, the account ADR 10 asks for: GitHub OIDC roles trusted per environment, a creation role held by guardrails and by a permissions boundary that every role it creates must carry, a sweep role that reads, deletes and rewrites a run's state but creates nothing, a versioned state bucket, budget alerts at $5 and $10, and a kill switch at $15 that attaches deny-all to the creation role. Its tests run against a mocked provider, and each guardrail is shown a planted violation it must catch (10 plants).
- The EKS validation run, built and not yet applied (`.github/workflows/eks-validation.yml`). It is dispatched by hand with `confirm: SPEND` from `main` only, keeps one state per run, and runs seven checks against the live cluster (`tests/eks/run.sh`): every Application synced and healthy, admission refusing its plants, IMDSv2 with a hop limit of 1 on the nodes, the ExternalDNS record, a Let's Encrypt certificate served by the NLB, Karpenter's NodePool and EC2NodeClass ready, and a Velero backup with objects in the bucket. Teardown is a separate job that runs whatever the first one did, then a residue check fails on anything the run left behind, and a cost report prices the run's resource-hours. A daily sweeper (`eks-sweeper.yml`) deletes what a broken run left and stays off until the repository variable `AWS_VALIDATION_ENABLED` is `true`.
- Terraform: `zone_id` uses an existing, delegated Route 53 zone instead of creating one, and refuses a zone whose name is not the domain; `iam_permissions_boundary` sets a permissions boundary on all seven IAM roles the module creates.
- `docs/engagement/`: an executive summary, discovery questions, a success plan whose eleven criteria map to e2e steps, an adoption plan from Docker Compose to a tenant, sizing, and handover.
- CodeQL (security-extended) for Python, Go and the workflows, on every push and weekly.
- The OpenSSF Best Practices badge, passing, and a README section on where a bug, a question or a change goes.

### Changed

- The README lists the known limitations in one place.
- ADR 5 cites [kyverno/kyverno#6554](https://github.com/kyverno/kyverno/issues/6554): Kyverno deletes its own webhook configurations when its admission controller scales to zero, by design since 1.9.
- CI's one Python package, PyYAML, is installed with `--require-hashes`.
- `scripts/diagnose.sh` prints the conditions of the object a waiting Argo CD sync waits on. Argo CD 3 keeps no per-resource health in the Application, so a timed-out run said only which object, never why.
- Charts: argo-cd 10.10.3, kube-prometheus-stack 92.3.1, opentelemetry-collector 0.176.0. The rendered manifests differ only in the chart version labels.

### Security

- `bootstrap-aws`, before it was ever released: the creation role could create a role without the guardrails, or rewrite the guardrails policy, and act through either. Every role it creates must now carry the permissions boundary, the bootstrap's own roles and policies are out of its reach, and the roles it may touch are limited to the run's prefix. Found in review before any account was created. What it still does not stop is written down in `terraform/bootstrap-aws/README.md`.

## [1.0.1] - 2026-10-13

### Fixed

- `bootstrap.sh` stores `PLATFORM_REPO_TOKEN` without a trailing newline. It was fed through a here-string, which appends one, and Argo CD sent the token as stored when it listed the remote's refs, so an Application pinned to a tag or a branch failed with "Invalid username or token" whenever the token was set, on a public repository as on a private one. A commit SHA needs no listing, which is why the e2e run, pinned to a commit, never saw it; the upgrade job, the first to read a tag, did.

### Added

- e2e step 8: Argo CD resolves the latest release tag with the credential the cluster holds.

### Changed

- The README and the threat model point at the two repositories next to the platform: the agent sandbox, and supply chain admission, which closes the threat model's open risk on unsigned images. ADR 3 says what the trust policy names rather than what the role is trusted by.

## [1.0.0] - 2026-10-12

### Added

- The platform as Argo CD ApplicationSets keyed on the cluster Secret: Envoy Gateway, cert-manager, External Secrets, Kyverno, kube-prometheus-stack, the OpenTelemetry Collector and Velero on every cluster; Karpenter, the AWS Load Balancer Controller and ExternalDNS on EKS.
- Kyverno CEL policies compiled into native ValidatingAdmissionPolicies: images by digest, requests and memory limits, probes, restricted Pod Security for tenants; a generated default-deny NetworkPolicy per tenant namespace.
- Tenants: one directory under `apps/` per team. The platform creates the namespace, its labels and quota, and an Argo CD project whose only destination is that namespace and which allows only the kinds a service needs, no RBAC among them. Every sync runs as the account its project names (Argo CD sync impersonation, enforced); a tenant's runs as a deployer whose Role grants the same kinds in its own namespace. The team's directory holds only what runs inside it.
- An SLO for the demo (availability and latency) with multi-window burn-rate alerts, unit-tested with promtool and shown to page in the kind e2e run.
- Terraform for EKS 1.37: VPC, cluster with access entries and KMS-encrypted Secrets, Graviton system node group, managed add-ons, Pod Identity for six controllers, Karpenter's AWS side, the Velero bucket and the Route 53 zone. Tested against a mocked provider; not yet applied to a real account.
- The kind e2e suite, run on every change and daily, and its upgrade job from the previous release.
- Static checks on the rendered manifests and the Terraform, each shown its planted violation.
- Runbooks for upgrade, rollback, restore and incident, and a hands-on guide whose three exercises run as written every week.
- Thirteen decision records, each ending with how the choice would be explained to a customer; a threat model with the check behind every control; a Well-Architected review with the evidence and the gaps.
